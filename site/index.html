Repeats its read of order_items 1.5M times, once per row of order_items.

Why
A nested loop is right for a few rows; at 1.5M repetitions one hash join over a single pass is far cheaper.
Fix
The query forces a loop join (OPTION (LOOP JOIN)): remove the hint and let the optimizer choose.
Verify
Run it with actual rows: a hash join, or far fewer executions of order_items.

Safe on production

Read-only by design. Careful by default.

Reads statistics only

Scans use catalog and statistics views with short lock timeouts. Estimated plans never execute anything.

Production is guarded

Statements Culprit can prove only read run read-only. Anything else on production needs an explicit confirmation.

Fixes are suggestions

Every fix is shown and copied, never applied, and uses online or concurrent operations where the server supports them.

Your data stays yours

Passwords live in the OS keychain, Entra ID uses your az login, and nothing about your servers leaves your machine.

Questions

Is it really free?

Yes. Culprit SQL Studio is open source under the MIT license: the app, the CLI and the MCP server.

Will it change anything in my database?

No. Scans only read statistics and catalog views. The SQL editor runs reads read-only, and anything that could change data on a production connection asks you first. Suggested fixes are shown, never applied.

Does my data leave my machine?

No. Culprit connects directly from your computer to your database. There is no account, no cloud service and no telemetry. Passwords stay in your operating system's keychain.

Which coding agents work with it?

Any agent that speaks the Model Context Protocol, including Claude Code, Cursor and Codex. Agents can also call the CLI directly, since every command has JSON output.

Can I add my own checks?

Yes. Checks and database engines plug in from outside without forking, and run, rank and explain exactly like the built-in ones. See the guide on GitHub.
