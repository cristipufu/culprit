What a diagnosis looks like — click to try

High 27% of database time · app/reports/order_summary.rb:84

A read from order_items times out on every run, at about 15 s.

Why
Its plan repeats a read of order_items 1.5M times, once per row: the query forces a loop join, where one hash join over a single pass would do.
Fix
Remove OPTION (LOOP JOIN) and let the optimizer choose.
Verify
Run it with actual rows: a hash join, and far fewer executions of order_items.
High 19% of database time · public.orders (480K rows)

Reads 480K rows of orders and discards 99.8% to find open orders for one customer.

Why
No index covers (customer_id, status): PostgreSQL scans the table 14,200 times an hour and filters in memory.
Fix
CREATE INDEX CONCURRENTLY orders_customer_id_status_idx ON public.orders (customer_id, status);
Verify
Test before building with culprit explain prod --sql "…" --with-index "CREATE INDEX …" (HypoPG switches to an Index Scan at 0.04% of the cost), or run culprit verify prod after rollout.
High Blocks writes on orders (12.4M rows, 8.2 GB) · migrations/0042_add_idx.sql:3

CREATE INDEX without CONCURRENTLY locks orders against writes while building.

Why
Checked offline against the production snapshot: orders has 12.4M rows and 340 writes/s. A standard index build blocks every INSERT, UPDATE and DELETE until it finishes.
Fix
Run culprit lint-sql prod --file migrations/ --write (or click Quick Fix in the editor) to rewrite as CREATE INDEX CONCURRENTLY.
Verify
culprit lint-sql prod --file migrations/ --fail-on high exits 0 (and emits SARIF 2.1.0 for GitHub PR annotations).
High 2 sessions waiting · longest wait 22 s on public.accounts

Session 71 has been idle in an open transaction for 22 s and holds up 2 sessions behind it.

Why
Session 71 ran UPDATE accounts SET balance = $1 WHERE id = $2 and never committed or rolled back; checkout workers are queued on its row lock.
Fix
Close the transaction in the application without waiting on network calls, and set idle_in_transaction_session_timeout = '30s'.
Verify
culprit blocking prod shows no chains waiting on idle in transaction sessions.

Findings

Slow queries, missing indexes and unsafe migrations, ranked by cost.

Runaway loops in plans, plan regressions, parameter sniffing, missing and unused indexes, N+1 query storms, lock pile-ups, implicit conversions, spills to disk, sequence or XID exhaustion, and migration DDL that would lock a hot table. Each finding comes with the evidence, a production-safe fix and how to verify it.

Plans

Execution plans that explain themselves.

Insights in plain words, a diagram that shows where the cost goes, and every operator's details one click away. Compare any two plans from SSMS, EXPLAIN or MySQL, or test a virtual index with --with-index to prove the planner uses it before building it.

What changed

Query regressions: drag across a chart, get the why.

Compare two periods and Culprit lists what got slower, what's new and what improved, next to the deploys and statistics updates around them: "Got 293× slower at 5:00 PM, when SQL Server switched from plan 163 to plan 198."

Live

Blocking and deadlocks: who is blocking whom, right now.

A wall of lock waits becomes one sentence and a tree: which session holds everyone up, why, and who waits behind it. Deadlocks get the same treatment, with the pattern named and the fix spelled out.

Frequently asked questions

What permissions does Culprit need?

Read access to the server's statistics. SQL Server needs VIEW SERVER STATE (VIEW DATABASE STATE on Azure SQL Database). PostgreSQL and TimescaleDB need pg_read_all_stats or pg_monitor; TimescaleDB also needs access to its information and size APIs. YugabyteDB uses pg_read_all_stats for broader statement visibility; native node resources require yb_db_admin or superuser. See the YugabyteDB coverage guide for cluster-view requirements. MySQL and MariaDB need PROCESS and SELECT on performance_schema. SQLite needs read access to the file. When a check can't run with your login, Culprit names the exact grant that unlocks it.

Do I need to install anything on the database server?

No. There's no agent or collector: Culprit connects like any client and reads the statistics the database already keeps (Query Store, pg_stat_statements, performance_schema). If a source is unavailable, Culprit explains what is missing and how to enable it where supported. TimescaleDB is detected through its existing PostgreSQL extension; YugabyteDB uses its own YSQL/DocDB sources and does not enable optional cluster views automatically. A SQLite file is opened read-only, with nothing added to your application.

Will it change anything in my database?

No. Scans only read statistics and catalog views. The SQL editor runs reads read-only, and anything that could change data on a production connection asks you first. Suggested fixes are shown, never applied.

Is it a monitoring tool?

It's an investigation tool: open it when something is slow, or let your coding agent ask it. History comes from Query Store and from Culprit's own saved scans, so there's no server to run and nothing collecting around the clock.

Does it work with Azure SQL and Amazon RDS?

Yes. Azure SQL Database and Amazon RDS for PostgreSQL are tested, Entra ID sign-in uses your az login, and Culprit can find your Azure and AWS databases with your existing CLI login.

How is it different from the SSMS Query Store reports or pgAdmin?

Those show the numbers. Culprit reads them for you: it ranks what costs the most time, explains it in one sentence, gives the fix and tells you how to verify it, with a shared workflow across supported databases and an explanation when a source cannot supply the evidence.

Which coding agents work with it?

Any agent that speaks the Model Context Protocol, including Claude Code, Codex and Cursor. Agents can also call the CLI directly, since every command has JSON output.

Is it really free?

Yes. Culprit SQL Studio is open source under the MIT license: the app, the CLI and the MCP server.
